# UI + API 智能扫描模式计划书

## 1. 计划定位

UI + API 智能扫描模式不是一个单纯的开发功能，也不是把爬虫、接口测试、UI 自动化简单拼在一起。它的定位是：让用户用自然语言描述目标 URL、业务模块和测试范围，由平台生成一轮可审计、可确认、可复用的测试战役（Test Campaign），再统一调度 UI 测试、API 测试和智能分析。

本计划书用于约束后续推进节奏，确保每一阶段都包含产品目标、用户价值、安全边界、验收指标和运营反馈，而不是只拆成开发任务。

## 2. 一句话目标

用户输入“测某个 URL 的某个业务模块”，平台能先生成可解释的测试计划，再在受控范围内执行 UI + API 联合测试，并沉淀为可复用的测试资产。

## 3. 非开发目标优先级

| 优先级 | 目标类型 | 目标说明 | 必须产出 |
|---|---|---|---|
| P0 | 用户价值 | 用户能用自然语言表达测试范围，不需要手工拼 API JSON 或 UI 步骤 | 可读测试计划、范围确认页 |
| P0 | 安全边界 | 默认不做破坏性操作，不做无限爬取，不跨授权域名 | allowlist、禁止动作、确认门禁 |
| P0 | 可解释性 | AI 为什么测这些路径、接口、断言必须可追溯 | 测试计划、来源标记、风险说明 |
| P1 | 可复用资产 | 扫描结果必须能沉淀为 API Case IR v2、Visual UI Case、Execution 记录 | 用例、资产、报告 |
| P1 | 质量度量 | 每轮扫描要能回答“覆盖了什么、漏了什么、失败了什么” | 覆盖摘要、失败摘要、人工复核项 |
| P2 | 自动化效率 | 在安全确认后减少人工编写重复用例的时间 | 生成耗时、复用率、误报率 |

## 4. 目标用户和典型场景

### 4.1 QA / 测试工程师

输入：

```text
测 https://staging.example.com 的用户管理模块，只覆盖登录、用户列表、新建用户，不要测删除。
```

期望：
- 平台生成 UI 路径和 API 接口测试计划。
- 标出哪些动作可能修改数据。
- 用户确认后执行 Smoke 或 Regression。
- 失败结果进入 Smart Ops 分析。

### 4.2 后端开发

输入：

```text
针对订单模块做灰盒接口扫描，范围是 /api/orders 和 /api/payments/mock，不执行真实支付。
```

期望：
- 优先从 API Asset 匹配接口。
- 生成 API Case IR v2 steps。
- 自动补充状态码、字段断言、变量提取。
- 不触发真实支付、删除、发短信等动作。

### 4.3 产品 / 业务验收人员

输入：

```text
帮我验证会员开通过程的主流程，重点看页面是否能走通，接口是否返回成功。
```

期望：
- 输出可读的业务路径，不展示过多底层技术细节。
- 最终报告能说明“哪些业务步骤通过、哪些失败、失败原因是什么”。

## 5. 模式定义

### 5.1 黑盒模式

只依赖目标 URL 和自然语言范围。

能力：
- 浏览页面。
- 识别导航、表单、按钮、主要业务路径。
- 通过浏览器网络请求提取 API 调用。
- 生成 UI smoke case 和候选 API step。

限制：
- 不读取源码。
- 不猜测隐藏接口。
- 不自动执行破坏性动作。

### 5.2 灰盒模式

依赖目标 URL、自然语言范围、环境配置、API Asset、已有 Test Case、历史执行结果。

能力：
- 从 API Asset 匹配相关接口。
- 从已有用例复用步骤。
- 根据历史失败补充边界用例。
- 生成 API Case IR v2 和 Visual UI Case。

这是首个推荐落地模式。

### 5.3 白盒模式

额外读取源码、路由、schema、模型和权限分支。

能力：
- 根据后端路由和 schema 推断参数边界。
- 根据前端页面和服务层定位真实调用链。
- 发现未覆盖分支。

限制：
- 初期只生成计划，不自动执行。
- 所有写操作、权限绕过、异常路径测试必须人工确认。

## 6. 用户流程

```text
1. 用户创建 Test Campaign
   - URL
   - 模块范围
   - 测试模式：黑盒 / 灰盒 / 白盒
   - 强度：Smoke / Regression / Deep
   - 禁止动作
   - 允许路径 / 域名

2. AI 生成测试计划
   - UI 路径
   - API 探测点
   - 数据准备
   - 断言策略
   - 风险动作
   - 不执行项

3. 用户确认计划
   - 删除或禁用危险步骤
   - 调整范围
   - 选择执行强度

4. 平台生成测试资产
   - API Case IR v2
   - Visual UI Case
   - HYBRID Campaign

5. 调度执行
   - Left Pupil 执行 API
   - Right Pupil 执行 UI
   - Dispatcher 负责模式分发

6. 结果分析
   - Smart Ops 汇总失败原因
   - 生成覆盖摘要
   - 标记可复用资产
```

## 8. 安全与治理边界

### 8.1 默认禁止

- 不做 DoS、压力轰炸或无限爬取。
- 不跨用户授权域名。
- 不自动执行真实支付、删除、发短信、发邮件、真实下单。
- 不绕过验证码、登录风控、权限控制。
- 不生成隐藏规避、逃逸检测或恶意利用逻辑。

### 8.2 默认需要人工确认

- POST / PUT / PATCH / DELETE。
- 表单提交。
- 文件上传。
- 账号创建、权限变更、支付、删除、消息发送。
- Deep 强度扫描。
- 白盒推断出的异常路径。

### 8.3 必须配置

- 域名 allowlist。
- 路径 scope。
- 请求速率限制。
- 最大页面数。
- 最大接口数。
- 最大执行时长。
- 禁止动作词表。

## 9. 和现有模块的关系

| 现有模块 | 在 Campaign 中的职责 |
|---|---|
| Design / Neural Design | 解析自然语言范围，生成测试计划草案 |
| API Asset | 提供接口资产匹配和 API step 来源 |
| API Case IR v2 | 作为 API steps 的内部标准结构 |
| API Auto | 展示、编辑、保存生成的 API cases |
| Visual UI | 展示、编辑、保存生成的 UI cases |
| Executions | 发起 Campaign 下的批量执行 |
| Dispatcher | 按 API / UI / HYBRID 分发执行 |
| Left Pupil | 执行 API 自动化 |
| Right Pupil | 执行 UI 自动化 |
| Smart Ops | 聚合失败原因、风险和修复建议 |
| Phoenix | 后续将稳定流程固化为可复用脚本 |

## 10. 阶段路线图

### Phase 0：概念验证和边界确认

目标：验证用户是否能用自然语言稳定描述测试范围。

非开发产出：
- 10 个真实业务模块样例。
- 用户输入模板。
- 禁止动作词表初版。
- Campaign 报告样例。

开发产出：
- 无需完整执行链路。
- 可以先用静态页面或接口草案生成测试计划。

退出标准：
- 80% 样例能生成可读、可确认的测试计划。
- 用户能明确判断哪些步骤会执行、哪些不会执行。

### Phase 1：灰盒计划生成 MVP

目标：接入 API Asset 和已有 Test Case，只生成计划，不自动执行。

非开发产出：
- 计划评审表。
- 风险动作确认规范。
- 测试范围填写规范。

开发产出：
- Campaign 创建页。
- AI 生成测试计划接口。
- API Asset 匹配结果展示。

退出标准：
- 每个 Campaign 都有 scope、风险项、候选 UI/API steps。
- 所有写操作默认进入人工确认。
- 不产生自动执行副作用。

### Phase 2：资产生成 MVP

目标：用户确认计划后，生成可编辑测试资产。

非开发产出：
- 资产命名规范。
- 生成用例复核清单。
- 误报/漏报记录表。

开发产出：
- 生成 API Case IR v2。
- 生成 Visual UI Case。
- API Auto / Visual UI 可编辑这些资产。

退出标准：
- 生成资产能被保存、刷新后仍可查看。
- API steps 不丢失 metadata/source 信息。
- UI steps 能被人工编辑后执行。

### Phase 3：受控执行 MVP

目标：用户确认后执行 Campaign。

非开发产出：
- 执行前确认规范。
- 环境隔离说明。
- 失败分类规则。

开发产出：
- Campaign 执行按钮。
- Execution batch 关联。
- API/UI/HYBRID 结果汇总。

退出标准：
- 执行结果可追溯到 Campaign 计划。
- 每个失败能定位到 UI step 或 API step。
- 报告能说明覆盖范围和未覆盖范围。

### Phase 4：反馈闭环和质量运营

目标：让 Campaign 成为持续测试资产，不只是一次性 AI 生成。

非开发产出：
- 周期性回归策略。
- 覆盖率观察指标。
- 用户反馈复盘机制。

开发产出：
- Campaign 历史。
- 失败趋势。
- Smart Ops 根因聚合。
- Phoenix 固化入口。

退出标准：
- 用户能复用历史 Campaign。
- 生成资产复用率可统计。
- 失败误报率逐步下降。

## 11. 验收指标

### 11.1 产品指标

| 指标 | 目标 |
|---|---|
| 用户能否独立创建 Campaign | 新用户 5 分钟内完成 |
| 测试计划可读性 | 人工评审通过率 >= 80% |
| 用户确认前危险动作暴露率 | 100% 必须展示 |
| 生成资产复用率 | MVP 后逐步达到 30%+ |

### 11.2 质量指标

| 指标 | 目标 |
|---|---|
| API Case IR v2 保存成功率 | >= 95% |
| UI Case 保存成功率 | >= 95% |
| Campaign 执行可追溯率 | 100% |
| 误报率 | 持续记录，Phase 4 前不硬性承诺 |
| 漏测反馈闭环 | 每轮手工反馈可回写 |

### 11.3 安全指标

| 指标 | 目标 |
|---|---|
| 未授权域名请求 | 0 |
| 未确认写操作执行 | 0 |
| 超出 scope 的路径执行 | 0 |
| 禁止动作执行 | 0 |
| 单 Campaign 最大请求量 | 受配置限制 |

## 12. Definition of Done

一个阶段不能只因为代码写完就算完成，必须同时满足：

1. 用户能看懂本阶段解决了什么问题。
2. 有可演示的端到端或半端到端流程。
3. 有明确不支持项。
4. 有安全边界。
5. 有失败处理方式。
6. 有至少一条真实或半真实样例验证。
7. 文档、接口、前端入口和测试结果一致。

## 13. 非目标

短期不做：

- 不做全站无限爬虫。
- 不做攻击式漏洞扫描。
- 不做绕过登录、验证码、风控的能力。
- 不做无确认的写操作自动执行。
- 不做自动删除、自动支付、自动发消息。
- 不直接替代人工测试计划评审。
- 不把所有 AI 输出直接当成可信测试用例。

## 14. 决策规则

后续任何需求如果只描述“开发什么接口、什么页面”，必须补齐以下问题后才能进入实现：

1. 用户为什么需要它？
2. 它减少了哪类手工工作？
3. 它会不会扩大误操作风险？
4. 它的结果如何复核？
5. 它如何沉淀为可复用资产？
6. 它失败时用户看到什么？
7. 它是否影响现有 API Auto、Visual UI、Executions 链路？

## 15. 防止“只剩开发目标”的治理看板

每个阶段开始和结束时都必须维护以下看板。只要任一 P0 项为空，该阶段不能进入开发或验收。

| 维度 | 阶段开始必须回答 | 阶段结束必须证明 |
|---|---|---|
| 用户价值 | 这阶段让用户少做了哪一步？ | 用户能否用一个真实场景完成这一步？ |
| 业务范围 | 这阶段服务哪个模块或角色？ | 是否有至少 1 个真实/半真实样例？ |
| 安全边界 | 哪些动作明确不做？ | 是否实际阻止了越界或危险动作？ |
| 可解释性 | AI 输出如何让用户复核？ | 报告是否说明“为什么测这些”？ |
| 可复用性 | 结果会沉淀成什么资产？ | 是否生成或更新了可复用 Test Case / Campaign？ |
| 失败体验 | 失败后用户怎么处理？ | 是否能看到失败原因、下一步建议和人工复核项？ |
| 度量 | 本阶段看哪个指标？ | 指标是否能被记录，而不是口头判断？ |

## 16. 首个建议实施范围

首个版本只做灰盒计划生成：

```text
输入：URL + 自然语言范围 + 强度 + 禁止动作
读取：API Asset + Environment + 现有 Test Case
输出：Campaign draft + 测试计划 + 候选 API/UI steps
执行：不自动执行，只允许用户确认后生成资产
```

这个范围能验证核心产品价值，同时避免一开始就进入高风险的自动扫描和破坏性执行。
