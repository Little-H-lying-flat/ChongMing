1. 系统概述 (System Overview)

1.1 定义与愿景

神经设计层 (Neural Design Layer) 是重明架构中负责 "想" (Think) 和 "审" (Review) 的顶层决策组件。它位于执行层之上，负责将产品需求文档 (PRD) 或自然语言需求转化为可执行的测试用例资产。

其核心设计哲学是 "PRD-Driven, Dev-Test-Unified" (需求驱动，测开一体)：
- 需求驱动：直接解析开发与测试共用的产品需求文档，而非单独的测试需求
- 意图理解：深度解析功能描述、数据模型、业务规则，推断隐含的边界条件与异常场景
- 智能生成：基于 LLM 自动生成多场景、多粒度的测试用例草稿
- 协作评审：引入 Critic Agent 进行自我评审，人工确认后固化

1.2 核心职责
- PRD 解析 (PRD Parsing)：解析产品需求文档，提取功能点、业务规则、数据模型
- 场景推理 (Scenario Inference)：基于需求推理正向流程、边界条件、异常场景
- 用例生成 (Case Generation)：自动生成多场景、多粒度的 TC-IR 用例集
- 质量评审 (Quality Review)：通过 Critic Agent 评估用例完备性与可执行性
- 资产固化 (Asset Solidification)：用户确认后，将 TC-IR 存入资产库

1.3 测开一体：输入即需求

重明的神经设计层打破传统"先有需求文档，再写测试用例"的模式：

传统模式：
  产品需求 → 开发实现 → 测试编写用例 → 执行测试
  ↓           ↓           ↓
  (信息丢失)  (理解偏差)   (覆盖不全)

重明模式：
  产品需求 (PRD) ──────────────────────────────┐
       │                                        │
       ▼                                        ▼
  开发实现                              AI 自动生成 TC-IR
       │                                        │
       └─────────── 同步验证 ──────────────────┘

优势：
- 需求同源：测试用例直接基于产品需求生成，避免理解偏差
- 覆盖全面：AI 自动推理边界条件和异常场景
- 实时同步：需求变更时，可重新生成对应用例

3. 详细流程设计 (Workflow Design)

3.1 智能用例生成流程 (The Intelligent Generation Flow)

这是神经设计层生成高质量测试用例的标准流程，采用 Draft → Review → Confirm 三阶段状态机。

=== Phase 1: Draft (草拟阶段) ===

Step 1: PRD 需求解析 (PRD Parsing)

输入示例（开发/测试共用的产品需求文档）：
---
1、背景描述
增加推荐的排课，建议学习时间，修改推荐排课的展示形式。

2、功能描述
2.1 建议学习时间
功能描述：根据该排课推荐出的时间，计算15天之后的日期。
数据来源：系统自动推荐的排课。
排序：排课结束正序。
数据模型：
原有展示字段不变，仅修改展示形式，去掉课程封面图片，见下方布局参考
建议完成时间：X年X月X号前完成
以当前排课生成为推荐内容之日起，计算15天之后的日期，在此展示
---

PRD Parser 输出结构化需求：
{
  "requirement_id": "REQ_SCHEDULE_001",
  "feature_name": "推荐排课 - 建议学习时间",
  "business_rules": [
    {
      "rule_id": "BR_001",
      "description": "建议完成时间 = 排课生成日期 + 15天",
      "formula": "suggested_deadline = created_at + 15 days"
    },
    {
      "rule_id": "BR_002", 
      "description": "排序规则：按排课结束时间正序排列",
      "sort_field": "end_time",
      "sort_order": "asc"
    }
  ],
  "ui_changes": [
    {
      "change_id": "UI_001",
      "description": "去掉课程封面图片",
      "action": "remove",
      "element": "课程封面图片"
    },
    {
      "change_id": "UI_002",
      "description": "展示建议完成时间",
      "format": "X年X月X号前完成"
    }
  ],
  "data_source": "系统自动推荐的排课",
  "suggested_test_modes": ["UI", "API", "HYBRID"]
}

Step 2: 场景推理 (Scenario Inference)

基于结构化需求，LLM 自动推理测试场景：

| 场景类型 | 推理来源 | 测试点 |
|---------|---------|--------|
| 正向流程 | BR_001 | 验证 +15 天计算结果正确 |
| 正向流程 | BR_002 | 验证按结束时间正序排列 |
| UI 验证 | UI_001 | 验证无课程封面图片 |
| UI 验证 | UI_002 | 验证日期格式正确展示 |
| 边界条件 | BR_001 | 跨月计算 (如1月20日+15=2月4日) |
| 边界条件 | BR_001 | 跨年计算 (如12月25日+15=次年1月9日) |
| 端到端 | 全流程 | 从生成到展示的完整验证 |

Step 3: TC-IR 自动生成

为每个场景生成 TC-IR 草稿（示例见: TC-IR-推荐排课建议学习时间需求示例.js）：

{
  "id": "DRAFT_TC_SCHEDULE_001",
  "status": "draft",
  "name": "建议学习时间计算逻辑验证",
  "source_requirement": "REQ_SCHEDULE_001 - BR_001",
  "mode": "API",
  "steps": [
    {"action": "call_api", "target": "获取推荐排课接口"},
    {"action": "verify", "target": "suggested_deadline", "condition": "equals", "expected_value": "${today + 15 days}"}
  ]
}

=== Phase 2: Review (评审阶段) ===

Step 4: Critic Agent 自评
- Critic Agent 对每个草稿进行多维度评估：

| 评审维度 | 检查项 | 评分 |
|---------|-------|------|
| 完备性 | 是否覆盖所有场景？ | 0.85 |
| 可执行性 | 步骤是否可自动化执行？ | 0.92 |
| 边界覆盖 | 边界条件是否充分？ | 0.78 |
| 断言明确性 | 预期结果是否可验证？ | 0.88 |

Step 5: 改进迭代
- 如果综合评分 < 0.80，自动触发改进：
  - Critic 输出改进建议：
    "建议补充：账号不存在场景、特殊字符用户名场景"
  - Generator 重新生成补充用例
  - 最多迭代 3 轮

=== Phase 3: Confirm (确认阶段) ===

Step 6: 人工确认
- 前端展示用例确认卡片：
  - 显示用例名称、步骤、预期结果
  - 提供 [确认] [修改] [拒绝] 三个操作
- 用户可以：
  - 直接确认：用例进入资产库
  - 请求修改：附加修改意见，返回 Draft 阶段
  - 拒绝：标记为 Abandoned，不生成资产

Step 7: 资产固化
- 确认的用例存入资产库，状态变为 "confirmed"
- 可被 Dispatcher 分发到左瞳/右瞳引擎执行

5. 关键模块实现细节

5.1 意图解析策略 (Intent Parsing Strategy)

采用 "Structured Extraction + Reasoning" 双阶段解析：

阶段1: 结构化抽取
- 使用 LLM 从自然语言中抽取关键字段
- Prompt 模板：
  """
  请从以下测试需求中提取结构化信息：
  需求：{user_input}
  
  请输出 JSON 格式：
  - target_feature: 被测功能名称
  - test_scope: 测试范围列表 (正向/边界/异常)
  - suggested_mode: 建议模式 (UI/API/HYBRID)
  - coverage_hints: 可能需要覆盖的场景提示
  """

阶段2: 场景推理
- 基于抽取结果，LLM 进行深度推理
- 推断隐含的边界条件与异常路径
- 参考历史用例库，补充遗漏场景

5.2 Critic Agent 实现

Critic Agent 使用独立的 LLM 调用，与 Generator 形成对抗评审：

class CriticAgent:
    def review(self, tc_draft: dict) -> CriticReport:
        prompt = f"""
        请作为测试专家评审以下测试用例：
        {json.dumps(tc_draft, ensure_ascii=False)}
        
        评审维度：
        1. 完备性：是否覆盖了功能的主要场景？
        2. 可执行性：步骤描述是否足够清晰，可被自动化执行？
        3. 边界覆盖：是否考虑了边界条件和异常输入？
        4. 断言明确性：预期结果是否具体、可验证？
        
        请输出 JSON 格式的评审报告。
        """
        return llm.generate(prompt)

10. 用例优先级自动推荐 (Priority Auto-Recommendation)

10.1 设计目标

智能推荐测试用例优先级，帮助测试团队聚焦最关键的测试：
- 基于多维度因素自动计算优先级
- 结合业务价值、变更风险、历史缺陷等信号
- 支持动态调整，适应敏捷迭代

10.2 优先级评分模型

=== 多因子加权模型 ===

PriorityScore = Σ(Factor_i × Weight_i)

| 因子 (Factor) | 权重 (Weight) | 计算方式 |
|--------------|---------------|---------|
| 业务影响度 (Business Impact) | 0.30 | 核心功能=10, 重要=7, 一般=4, 边缘=1 |
| 代码变更热度 (Change Hotspot) | 0.25 | 基于 Git commit 频率和范围 |
| 历史缺陷密度 (Defect Density) | 0.20 | 该模块历史 Bug 数量 / 代码行数 |
| 功能复杂度 (Complexity) | 0.15 | 圈复杂度、代码耦合度 |
| 用户使用频率 (Usage Frequency) | 0.10 | 基于埋点/日志的使用统计 |

=== 优先级映射 ===

| 得分区间 | 优先级 | 说明 |
|---------|--------|------|
| 8.0 - 10.0 | P0 | 必须测试，阻塞发布 |
| 6.0 - 7.9 | P1 | 高优先级，应覆盖 |
| 4.0 - 5.9 | P2 | 中优先级，资源允许时覆盖 |
| 0.0 - 3.9 | P3 | 低优先级，可延后 |

10.3 核心实现

class PriorityRecommender:
    """用例优先级推荐器"""
    
    def __init__(self, config: PriorityConfig):
        self.weights = config.factor_weights
        self.analyzers = {
            "business_impact": BusinessImpactAnalyzer(),
            "change_hotspot": ChangeHotspotAnalyzer(),
            "defect_density": DefectDensityAnalyzer(),
            "complexity": ComplexityAnalyzer(),
            "usage_frequency": UsageFrequencyAnalyzer()
        }
    
    def recommend_priority(self, test_case: DraftTCIR, context: PriorityContext) -> PriorityResult:
        """为测试用例推荐优先级"""
        scores = {}
        
        # 计算各因子得分
        for factor_name, analyzer in self.analyzers.items():
            scores[factor_name] = analyzer.analyze(test_case, context)
        
        # 加权求和
        total_score = sum(
            scores[factor] * self.weights.get(factor, 0)
            for factor in scores
        )
        
        # 映射到优先级
        priority = self._map_to_priority(total_score)
        
        return PriorityResult(
            test_case_id=test_case.id,
            score=total_score,
            priority=priority,
            factor_scores=scores,
            explanation=self._generate_explanation(scores, priority)
        )
    
    def _map_to_priority(self, score: float) -> str:
        if score >= 8.0: return "P0"
        if score >= 6.0: return "P1"
        if score >= 4.0: return "P2"
        return "P3"
    
    def _generate_explanation(self, scores: dict, priority: str) -> str:
        """生成优先级解释"""
        top_factors = sorted(scores.items(), key=lambda x: x[1], reverse=True)[:2]
        factor_names = {"business_impact": "业务影响度高", "change_hotspot": "近期频繁变更",
                       "defect_density": "历史缺陷多", "complexity": "功能复杂", "usage_frequency": "使用频率高"}
        
        reasons = [factor_names.get(f[0], f[0]) for f in top_factors]
        return f"建议 {priority}：{', '.join(reasons)}"

10.4 因子分析器

=== 业务影响度分析 ===

class BusinessImpactAnalyzer:
    """基于 LLM 分析功能的业务影响度"""
    
    def analyze(self, test_case: DraftTCIR, context: PriorityContext) -> float:
        prompt = f"""
        请评估以下测试用例对应功能的业务影响度 (0-10分):
        
        功能名称: {test_case.name}
        功能描述: {test_case.description}
        涉及模块: {test_case.target_feature}
        
        评分标准:
        - 10-8分: 核心功能 (登录/支付/核心交易)
        - 7-5分: 重要功能 (用户信息/订单查询)
        - 4-2分: 一般功能 (设置/偏好/辅助)
        - 1-0分: 边缘功能 (关于页/帮助)
        
        仅输出数字分数。
        """
        
        score_text = self.llm.generate(prompt)
        return float(score_text.strip())

=== 代码变更热度分析 ===

class ChangeHotspotAnalyzer:
    """基于 Git 历史分析变更热度"""
    
    def analyze(self, test_case: DraftTCIR, context: PriorityContext) -> float:
        # 获取相关代码文件
        related_files = context.get_related_files(test_case.target_feature)
        
        total_score = 0
        for file_path in related_files:
            # 查询最近 N 天的 commit 数量
            commits = self.git_analyzer.get_recent_commits(file_path, days=14)
            
            # 变更行数
            lines_changed = sum(c.additions + c.deletions for c in commits)
            
            # 计算热度分数 (归一化)
            file_score = min(10, len(commits) * 1.5 + lines_changed / 100)
            total_score += file_score
        
        return min(10, total_score / max(1, len(related_files)))

=== 历史缺陷密度分析 ===

class DefectDensityAnalyzer:
    """基于历史 Bug 数据分析缺陷密度"""
    
    def analyze(self, test_case: DraftTCIR, context: PriorityContext) -> float:
        module = test_case.target_feature
        
        # 查询该模块历史缺陷
        defects = context.defect_tracker.query_by_module(module, days=90)
        
        # 严重程度加权
        weighted_count = sum(
            self._severity_weight(d.severity) for d in defects
        )
        
        # 归一化到 0-10
        return min(10, weighted_count / 2)
    
    def _severity_weight(self, severity: str) -> float:
        return {"critical": 4.0, "major": 2.0, "minor": 1.0, "trivial": 0.5}.get(severity, 1.0)

async def generate_draft_with_priority(state: DesignState) -> DesignState:

    return state.update(tc_ir=tc_ir)
